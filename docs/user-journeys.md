# Пользовательские маршруты NIR

Этот документ отвечает на практический вопрос: «Я открыл Mac — что я реально
могу сделать сейчас?» На 24 сентября 2026 года публичной сети NIR, публичной
очереди майнинга, официального faucet и готового consumer-приложения нет.
Репозиторий даёт только локальную сеть без ценности и инструменты разработчика.
Локальные NIR нельзя считать деньгами, продавать или обещать как доход.

Машиночитаемый срез статусов находится в
[`feature-status.json`](feature-status.json). В нём `implemented + local-only`
означает, что путь выполняется в репозитории на локальной devnet;
`partial + local-only` — реализована лишь часть механизма или модель без полного
пользовательского сервиса; `specified-only + planned` — есть только проектный
маршрут, пользоваться им нельзя.

## Словарь без жаргона

- **Vault** — зашифрованный файл с ключом кошелька. Это секрет даже в
  зашифрованном виде.
- **Адрес** — публичный идентификатор вида `nir1…`; его можно показывать.
- **Локальная devnet** — тестовая сеть на этом Mac. Её единицы не имеют ценности.
- **Bridge** — локальная программа между браузерным интерфейсом и vault. Пароль
  вводится в Terminal, а не на странице.
- **Node** — узел, который хранит и проверяет цепочку и принимает операции.
- **Validator** — отдельный процесс, который проверяет блок и подписывает его
  финализацию. Четыре процесса на одном Mac не равны четырём независимым людям.
- **Stake** — временно заблокированные NIR для получения лимита операций; это не
  вклад и не проценты.
- **Network Credits / Transfer Credits** — возобновляемый лимит переводов без
  обычной комиссии, не отдельные монеты.
- **Proof / checkpoint** — данные, позволяющие локально проверить состояние, а
  не просто поверить одному серверу.

## 1. Первый запуск на Mac — локальный учебный контур

**Статус: реализовано локально.** Нужны macOS, Terminal, Python 3.11+ и Node.js
26+. Команды запускаются из корня уже скачанного репозитория. Выберите отдельные
пути вне Git для node и vault; не используйте эти ключи для реальной ценности.

1. Проверьте окружение: `python3 --version` и `node --version`.
2. Проверьте код: `python3 -m unittest discover -s tests -v`, затем
   `npm run test:chain`.
3. Один раз создайте локальный узел:
   `npm run node:init-dev -- /absolute/path/nir-local-node`.
4. В Terminal 1 запустите его:
   `npm run node:serve -- /absolute/path/nir-local-node`.
5. В Terminal 2 создайте vault:
   `npm run wallet:create -- /absolute/private/path/personal.nirvault.json`.
   Придумайте длинный уникальный пароль и сохраните его вне браузера.
6. В Terminal 3 запустите интерфейс: `npm run wallet:preview`, затем откройте
   `http://127.0.0.1:8765`.
7. В Terminal 4 запустите bridge с genesis как trust anchor:
   `npm run wallet:bridge -- /absolute/private/path/personal.nirvault.json 8788 http://127.0.0.1:8765 /absolute/path/nir-local-node/genesis.json`.
8. В интерфейсе выберите подключение vault и введите одноразовый восьмизначный
   код из Terminal 4. Код живёт две минуты; пароль vault сюда не вводится.
9. Скопируйте адрес из `wallet:address` и в отдельном Terminal вызовите локальный
   faucet (замените `nir1...` полным адресом):
   `curl -H 'content-type: application/json' -d '{"recipient":"nir1..."}' http://127.0.0.1:8787/v1/faucet`.
   Faucet выдаёт не более 10 тестовых NIR один раз свежему адресу.

Ожидаемый результат: интерфейс показывает адрес, сеть `valueless-devnet`,
проверенный или явно помеченный single-node баланс и высоту. Если порт занят,
остановите лишний процесс или выберите допустимый loopback-порт. Если pairing
истёк или было пять ошибок, перезапустите bridge. Безопасный выход: нажмите
Disconnect, остановите bridge и preview через `Ctrl+C`; vault останется на диске.

## 2. Кошелёк, получение и отправка NIR

**Статус: реализовано локально; публичного кошелька и публичной сети нет.**

### Получить на адрес

1. Показать адрес без расшифровки vault можно командой
   `npm run wallet:address -- /absolute/private/path/personal.nirvault.json`.
2. В интерфейсе откройте **Receive**. Для простого получения передайте полный
   адрес отправителю и отдельно сверьте сеть.
3. После локального перевода обновите состояние. Доверять следует только
   доказанному checkpoint; если genesis не передан bridge, UI честно помечает
   данные как полученные от одного узла.

Ошибка в адресе необратима после финализации. Не сокращайте адрес при сверке.

### Отправить

1. Откройте **Send**, введите адрес и сумму. Одна NIR равна `100000000`
   атомарных единиц.
2. Дождитесь симуляции и проверьте сеть, полный адрес, сумму, fee, nonce и
   итоговый баланс.
3. Запросите подпись. В Terminal bridge ещё раз проверьте сводку, напечатайте
   `SIGN`, затем введите пароль скрытым вводом.
4. UI сначала показывает подписанный JSON. Только отдельная кнопка отправляет
   его в локальный узел после свежей проверки сети.

Ожидаемый результат: операция финализируется, история и оба баланса обновляются.
Неверный nonce, нехватка средств/комиссии, другая сеть, повтор transaction id или
устаревшая симуляция дают отказ без автоматической повторной подписи. Безопасный
выход до Submit: отменить review или Disconnect; подпись сама ничего не отправляет.
CLI `wallet:sign` тоже существует, но лишь формирует подписанную транзакцию и не
синхронизирует баланс и не отправляет её.

## 3. Платёжный запрос и QR

**Статус: реализовано локально.** Запрос — подписанный счёт, а не списание денег.

Получатель открывает **Receive**, задаёт сумму, memo и срок от 1 минуты до 30
дней, проверяет симуляцию и подтверждает подпись в Terminal bridge. Затем он
передаёт JSON либо все QR-фрагменты плательщику. В запросе нет приватного ключа.

Плательщик открывает **Send → Paste signed payment request**, вставляет полный
JSON или все QR-фрагменты и выбирает **Verify and fill**. Bridge проверяет
подпись, сеть, адрес, сумму, id и expiry; только затем поля перевода заполняются.
Далее действует обычный маршрут Send с отдельной подписью и Submit.

Просроченный запрос, пропущенный/повторный QR-фрагмент, изменённое memo, другая
сеть или лишнее поле отклоняются. Запрос можно просто закрыть: он не резервирует
средства. Магазин должен сам не допускать повторное погашение одного request id.

## 4. Офлайн-подпись

**Статус: реализовано локально, не аудитировано для реальных средств.** Нужны
сетевой Mac с wallet UI и отдельное доверенное устройство без сети с проверенной
копией NIR signer и vault.

1. На сетевом Mac получите proof-backed симуляцию и выберите экспорт офлайн-
   пакета. Пакет действует не более 15 минут.
2. Перенесите JSON или все QR-фрагменты на офлайн-устройство без облачных
   заметок и почты.
3. Сначала проверьте: `npm run offline:verify -- request.nir.json`.
4. Подпишите в интерактивном Terminal:
   `npm run offline:sign -- wallet.nirvault.json request.nir.json signed-package.json`.
5. Верните только signed-package, импортируйте его в UI. Кошелёк сверит точное
   намерение, checkpoint, commitment и публичную подпись.
6. На этом текущий UI останавливается: он умеет проверить и показать
   подписанную транзакцию, но не пытается её отправить. Копируемого
   beginner-safe broadcast-маршрута для offline package в репозитории пока нет.

При expiry, другой сети/checkpoint, неизвестном поле, изменённом nonce или
неполном QR-наборе прекратите процесс и экспортируйте новый пакет. Не «чините»
JSON вручную. Watch-only файл без приватного ключа создаётся командой
`npm run offline:watch-export -- wallet.nirvault.json checkpoint.json watch-only.json`.

## 5. Stake, Network Credits и делегирование

**Статус: реализовано локально с тестовыми параметрами.** В UI откройте
**Resources**. Можно: заблокировать NIR, сделать перевод за credit, выдать
другому адресу лимит credits, отозвать его или начать выход из stake.
Однако starter faucet выдаёт новому адресу максимум 10 NIR один раз. После оплаты
комиссии этого недостаточно для одного целого credit, поэтому beginner journey может
проверить формы и отказы, но не честно обещать credit-paid transfer.

Текущая модель даёт 10 переводов на 100 NIR за 720 блоков, максимум 100
credit-переводов в блоке; это не production-параметры. Делегат не получает
доступ к stake или балансу владельца. При каждом действии сверяйте owner,
delegate, лимит, fee, nonce и сеть в Terminal bridge, затем отдельно отправляйте
подписанный JSON.

Для выхода создайте unstake request: сумма перестанет давать credits сразу,
комиссия удержится из неё. Дождитесь показанного `unlockHeight`, затем нажмите
claim. Одновременно допускается один выход. Ранний claim, исчерпанный credit,
лимит ниже уже потраченного или нехватка stake отклоняются. При компрометации
делегата установите лимит `0`; уже финализированные переводы это не отменит.

## 6. Нативные активы

**Статус: реализовано локально для protocol 25; starter devnet запускается
на protocol 24.** В **Resources → User assets** есть proof-backed просмотр и формы
create, mint, transfer, burn и безвозвратного revoke mint authority.

1. Обычный quickstart не даёт копируемой команды активации protocol 25. Реализованные
   правила можно безопасно прогнать точной командой:
   `node --test tests/native-asset-tools.test.mjs tests/native-assets-adversarial.test.mjs tests/native-assets-model.test.mjs`.
2. Заполните форму; metadata — только 32-байтовый hash, а не доверенное имя.
3. Проверьте NIR fee, asset id, cap, supply, authority, балансы и предупреждения.
4. Браузер не подписывает asset-операции. Экспортируйте пакет и пройдите маршрут
   офлайн-подписи выше.
5. Импорт пока только проверяет подпись; UI не публикует asset-операцию. До
   появления отдельного проверенного broadcast-маршрута это не end-to-end функция для
   обычного пользователя.

Protocol 24, недоказанное/устаревшее состояние, over-cap, неверная authority и
несовпавший checkpoint дают отказ. Burn и revoke необратимы; безопасный выход —
отменить preview до экспорта. Никаких smart contracts, биржи или прав
администратора менять чужие балансы здесь нет.

## 7. Локальный узел

**Статус: реализовано локально.** Базовый путь — `node:init-dev`, затем
`node:serve`. Узел слушает только `127.0.0.1:8787`, хранит блоки, перепроверяет
цепь после рестарта и даёт wallet RPC. `DEVNET-KEYS.json` содержит незашифрованные
тестовые ключи: не публикуйте каталог и никогда его не финансируйте.

Ожидаемый результат — `/health` сообщает `valueless-devnet`. Wildcard/public
bind отклоняется. Если каталог повреждён, не удаляйте файлы наугад: остановите
узел, сохраните копию и используйте verify/backup-процедуры. Публичный доступ
требует отдельного TLS edge и операторской настройки; встроенный localhost
сервер ею не является.

## 8. Валидатор

**Статус: многопроцессный валидатор реализован локально; независимая публичная
сеть только планируется.** Для учебного запуска выполните
`npm run network:init-dev -- .nir-network`, запустите в четырёх Terminal:
`npm run network:validator -- .nir-network/validators/validator-0 8791`,
`npm run network:validator -- .nir-network/validators/validator-1 8792`,
`npm run network:validator -- .nir-network/validators/validator-2 8793` и
`npm run network:validator -- .nir-network/validators/validator-3 8794`, затем coordinator по процедуре
[`network.md`](network.md).

Ожидаемый результат: proposal получает prepare- и commit-кворум `2N/3 + 1`, а
каждый процесс хранит собственный журнал. Ошибка TLS pin, конфликт tip,
недостаточный quorum или занятый порт останавливают продвижение. Безопасный
выход — `Ctrl+C` и сохранение каталогов; не копируйте validator private keys.
Четыре процесса, ключа или облачных VM одного владельца не доказывают
независимость. Production onboarding требует ceremony, подписанный release,
отдельные TLS/transport/finality keys и внешние операционные проверки.

## 9. «Майнинг интеллекта»: что реально проверяется

**Статус: правила и демонстрация частично реализованы локально; пользовательский
майнер, задания и доход — planned.** Сейчас доступны read-only
`npm run mine:preflight` и `npm run mine:demo`. Вторая команда создаёт локальные подписанные блоки и evaluation
receipts, но не обучает модель, не подключается к peers и не приносит ценные NIR.

Планируемая проверка — не общий IQ-тест ИИ. Кандидат сначала фиксирует точную
версию артефакта, canonical content, baseline и bond. После финализации случайно
назначенные независимые операторы запускают замороженные baseline и candidate на
свежих скрытых заданиях. Проверяются измеримый прирост, широта результата,
воспроизводимость, новизна, заявленные ресурсы и обязательная safety policy.
Один подтверждённый critical safety failure запрещает reward. После принятия
ещё действует окно оспаривания и escrow; заявление автора или число GPU само по
себе ничего не создаёт.

Планируемые роли: capability author, reproduction operator, challenge author,
safety evaluator, safety investigator, fraud challenger и payment-node operator.
Публичных контейнеров, hardware preflight, job queue, bootstrap peers, faucet,
регистрации ролей и assignment service сейчас нет. Поэтому не вводите ключи или
модельные секреты на сайтах «NIR mining» и не покупайте ранний доступ.

## 10. Safety bounty

**Статус: локальная расчётная модель и тесты есть; приём реальных отчётов и
публичная bounty-программа planned.** Локальная модель подтверждённой critical
находки распределяет bond кандидата: 70% reporter, 10% независимым evaluators,
не менее 20% burn; новые NIR не выпускаются. Саморепорт собственного кандидата,
повтор evidence и неподтверждённая находка должны отклоняться.

Будущий пользователь сначала приватно commits evidence, затем назначенный
комитет воспроизводит его не раньше заданного окна. Сейчас нет адреса подачи,
портала, гарантированной выплаты или безопасного disclosure-канала. Не
публикуйте уязвимость по выдуманному адресу; используйте только официальную
политику, когда она будет опубликована.

## 11. Agent Mandates и подключение ИИ к приложениям

**Статус: Stage 2 — изолированная локальная модель; chain, wallet и пригодное
для пользователя подключение planned.** Текущий кошелёк не умеет выдать агенту
mandate, а текущая chain его не принимает. Нельзя давать ИИ vault, главный ключ,
пароль или пополненный счёт.

Задуманный безопасный путь таков: пользователь выбирает приложение; кошелёк
создаёт отдельный delegate-key; пользователь задаёт разрешённые действия и
получателей, максимум одной операции, общий spend/fee budget, частоту, expiry и
минимальный остаток. ИИ создаёт только typed intent. Отдельный policy engine
делает точную симуляцию, а изолированный signer подписывает байты лишь внутри
лимитов. Каждый результат получает receipt; owner может revoke/freeze, а
recovery/rotation инвалидирует старую policy epoch.

Stage 2 сейчас моделирует только escrowed transfer к allowlisted payees с
лимитами суммы/fee, expiry, owner revoke/close и cleanup. Он принимает уже
проверенную авторизацию и не реализует signed schemas, proof/snapshot,
controller sets, wallet signer, trading, freeze/recovery или protocol-v26.
Payment mandate никогда не даёт права майнить или оценивать собственную работу.

## 12. Backup и recovery

### Кошелёк

**Статус: single-account vault backup/restore реализован локально; hardware key
и готовый consumer recovery остаются planned.** Проверьте vault командой
`npm run wallet:verify -- VAULT`. Создайте новую резервную копию на отдельном
носителе:

`npm run wallet:backup -- VAULT NEW_BACKUP nir-testnet GENERATION`

Храните отдельно address, network и последний generation. Восстановление пишет
только в новый путь:

`npm run wallet:restore -- BACKUP NEW_VAULT nir-testnet EXPECTED_ADDRESS MIN_GENERATION`

Неверный пароль, сеть/address, старый generation, существующий target,
небезопасные permissions или изменённый файл дают отказ. Не перезаписывайте
оригинал; сначала выполните `wallet:verify` на восстановленной копии. В repo
также есть отдельный 2-of-3 `vault:create` для операторских/treasury сценариев;
это не автоматическое восстановление обычного browser wallet.

### Узел

**Статус: локальный backup, проверка и remote restore drill реализованы.**
Остановки live-node для экспорта не требуется по документации, но target должен
быть новым: `npm run node:backup -- LIVE NEW_BACKUP`, затем
`npm run node:verify-backup -- NEW_BACKUP`. Реальная отказоустойчивость требует
минимум двух независимо управляемых storage operators и команды
`backup:drill-remote`; две папки на одном Mac независимостью не являются.
Конфликтующие receipts, stale backup или mismatch hash должны останавливать
restore, а не выбирать «самую новую» копию.

## 13. Обновления

**Статус: проверяемая локальная release/install/update цепочка реализована;
обычный auto-update, platform signing/notarization и публичный канал planned.**
Production update устанавливается в новый каталог, требует подписанный release,
точный hash текущей установки, рост SemVer и ту же network/genesis. Например,
оператор использует `release:install-production-update-wallet` или
`release:install-production-update-node`, затем точную команду
`release:verify-production-wallet-install` или `release:verify-production-node-install` и только после этого
внешний supervisor переключает active target.

Инструмент не останавливает процесс, не переключает приложение, не удаляет
предыдущую версию и не обновляет внешний доверенный anchor. При rollback,
неверном signer/hash, смешанной lineage или изменённых файлах безопасный выход —
оставить старую проверенную generation активной и расследовать расхождение.
Никакого URL «скачать последнюю NIR» или готовой notarized macOS-сборки сейчас
нет; их нельзя подставлять заранее.

## Итог для обычного пользователя

Сегодня на Mac можно безопасно изучать только valueless localhost: создать и
резервировать vault, получить тестовые единицы, подписать/отправить тестовый
платёж, попробовать payment request, проверку offline signing, формы stake/credits и активов,
узел и локальный validator rehearsal. Интеллект-майнинг, safety bounty и Agent
Mandates нельзя подключить к внешним приложениям как готовый сервис. Переход к
публичному использованию начинается только после опубликованного подписанного
